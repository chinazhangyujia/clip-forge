# ClipForge — MVP Requirements

## Project overview

ClipForge takes a long course recording (typically 2–4 hours of video with audio) and automatically produces a set of short, social-media-ready clips. The user provides a high-level cutting prompt that describes how the long video should be segmented; the system handles transcription, segmentation, and packaging.

The target user is a course creator who currently does this work by hand and wants to reclaim hours per upload.

## Local-first architecture

ClipForge runs as a **local-first desktop app**. Heavy compute (ffmpeg, Whisper) executes on the user's machine; the only cloud calls are to LLM providers for cutting decisions and metadata generation. This avoids 5–20 GB uploads, cross-border data residency concerns, and ongoing cloud storage costs.

The same app supports two regional configurations without rewrites:

1. **Dev / demo (US)** — the configuration we are currently shipping. The app runs on a developer machine for POC and demos. Cloud LLM calls go to US-hosted services (Anthropic Claude).
2. **Production (China, mainland)** — the product owner is based in China. The same desktop app runs on his Mac/Windows machine. Cloud LLM calls go to Chinese-accessible providers.

**Architectural principle:** every cloud dependency used in the dev configuration must have a feasible Chinese equivalent. The local pipeline is identical in both regions.

| Capability | US dev | China prod |
|---|---|---|
| LLM (long context) | Anthropic Claude | Qwen / Kimi / DeepSeek / GLM |
| Speech-to-text | Bundled `whisper.cpp` | Bundled `whisper.cpp` |
| Video / audio processing | Bundled ffmpeg | Same |
| Workspace storage | User-picked local directory | Same |
| Job execution | In-process Python worker | Same |
| ML model distribution | Hugging Face download on first launch | Mirrored on Alicloud OSS (Hugging Face is throttled / blocked in mainland China) |

The only runtime swap point is the cloud LLM provider, which lives behind a thin interface and is selected per build configuration.

## MVP feature scope

Three features ship in the MVP. Anything not listed here is out of scope.

### 1. Core: prompt-driven clip cutting

- **Input:** one long video file (with audio guaranteed to be present), plus a user-provided cutting prompt that describes the desired segmentation logic (e.g. "cut into clips around each distinct teaching point, 30–90 seconds each").
- **Process:**
  - Extract audio with ffmpeg.
  - Transcribe with word-level timestamps.
  - Send transcript + cutting prompt to an LLM that returns a list of `{start, end, title}` segments. For long transcripts, use a map-reduce pass (chunk → candidate segments → re-rank globally) so the full transcript fits within practical context limits.
  - Snap LLM-proposed timestamps to the nearest sentence boundary, with a small lead-in / lead-out aligned to silence gaps so cuts don't feel abrupt.
  - Slice the source video at each interval with ffmpeg.
- **Output:** N short video clips, each ready to feed into the packaging step.

### 2. Manual clip boundary tuning

After the auto-cutter produces its initial set of clips, the user can adjust any clip's start / end timestamps before downloading. This is a purely local interaction — no LLM call, no pipeline re-run. The intended flow is: AI cut → review and tune per clip → download.

- **Input:** A clip's current `{startSec, endSec}` from `cuts.json`, plus the source video's full duration and the word-level transcript.
- **UI:** In the Clip Detail view, a trim track shows a windowed view of the source — `clipDuration + max(clipDuration × 0.5, 15s)` of margin on each side, clamped to `[0, sourceDurationSec]`. The clip is rendered as a draggable band; the auto-cutter's original bounds are marked as ticks inside it. Two handles let the user shift either boundary, and `mm:ss.s` numeric inputs mirror the handles. Either boundary can move freely within `[0, sourceDurationSec]` — the user can extend a clip beyond the auto-cutter's original bounds, not just shrink it. When a handle is dragged to the edge of the visible window, the window auto-pans to follow it (the non-dragged boundary stays fixed in source-time). Overlap with neighboring clips is allowed; neighbors that fall within the visible window render as faint, non-interactive context bands.
- **Snap-to-sentence:** Defaults on; drags snap to sentence boundaries derived from the same word-level transcript the auto-cutter used. The user can toggle to frame-precise mode.
- **Persistence:** Edits update `{startSec, endSec}` in `cuts.json`. The source video is not re-sliced until the user downloads the clip.
- **Output:** The trimmed clip flows into packaging (feature 3) the same way an auto-cut clip does.

### 3. Content packaging per clip

For each clip, produce the metadata and visual treatment a creator would otherwise add by hand:

- **Hook / title** generated by an LLM from the clip transcript.
- **Description and hashtags** per platform target. MVP supports a configurable set of platform profiles (US dev: at least one of TikTok / YouTube Shorts / Instagram Reels; China prod: at least one of Douyin / Xiaohongshu / Bilibili).
- **Thumbnail frame** auto-selected from the clip — pick a frame where the instructor's face is well-lit and the mouth is roughly closed (use detection confidence + simple brightness heuristics).
- **Cold-open hook overlay** for the first ~1.5s of the clip — short text overlay generated by the LLM, rendered with ffmpeg.

Burned-in captions are intentionally **not** in MVP scope — TikTok / Douyin / Reels / Shorts all ship native auto-caption with better styling than we'd produce, so creators can rely on those at post time.

## Out of scope for MVP

The following were considered but are deferred. Do not build these without an explicit decision to expand scope:

- Voice isolation, denoising, loudness normalization.
- Filler-word removal ("um" / "uh") with audio re-stitching.
- Burned-in captions (creators use platform-native auto-caption on TikTok / Douyin / YouTube Shorts / Xiaohongshu).
- Highlight scoring / clip ranking by predicted shareability.
- Multi-clip timeline editing (splitting one clip into two, merging adjacent clips, reordering, cross-clip drag-and-drop). Single-clip boundary tuning is in scope — see MVP feature 2.
- Direct posting to social platforms via TikTok / YouTube / Instagram / Douyin / Xiaohongshu APIs.
- Multi-user accounts, auth, billing.
- Performance feedback loop (learning from per-clip metrics).

## Non-functional requirements

- **Long-running jobs run on a background worker process**, not on the HTTP request handler. The UI enqueues jobs and polls or subscribes for status.
- **The workspace is a user-picked local directory**, configured at first launch. There is no cloud upload step.
- **All artifacts (source media, transcripts, cut lists, clips, processed variants) live as plain files inside the workspace directory** — never on a remote backend.
- **Cloud LLM calls sit behind a `Provider` interface** so we can swap Claude ↔ Qwen / Kimi / DeepSeek via config. Local filesystem access is abstracted via a `WorkspaceProvider` so the same UI works against the browser File System Access API (Phase 0 web build) and the Tauri filesystem API (Phase 1+ desktop build).
- **The pipeline must produce deterministic intermediate artifacts** (`transcript.json`, `cuts.json`, per-clip metadata JSON) that can be inspected and regenerated independently. This is essential for prompt iteration, the eval set described below, and the per-clip tuning UI (MVP feature 2).

## Evaluation

We will maintain a small eval set of "good clip vs. bad clip" examples sourced from the product owner's existing manually-cut clips. The eval set drives prompt iteration on the cutting and packaging steps. Building the eval set is part of MVP work, not a follow-up.

## Tech stack

- **Backend:** Python 3.11+, FastAPI, uvicorn. Background worker runs in-process; lightweight job state stored in SQLite inside the workspace directory.
- **Frontend:** TypeScript, Next.js (App Router), Tailwind.
- **Desktop shell (Phase 1+):** Tauri — wraps the Next.js UI in a native webview and runs the FastAPI backend as a sidecar process.
- **Repo layout:** monorepo with `backend/` (FastAPI) and `web/` (Next.js); a `desktop/` Tauri shell will be added in Phase 1.

## Distribution & packaging

ClipForge ships as a desktop app that wraps the existing Next.js + FastAPI stack in a [Tauri](https://tauri.app/) shell. The app contains every dependency the user needs — they install ClipForge, they don't install Python / ffmpeg / Whisper separately.

### Platform support

- **macOS** (Intel and Apple Silicon)
- **Windows** (x64)

Linux is not an MVP target but stays achievable since the underlying tooling is cross-platform.

### What ships in the installer

| Component | Approximate size | Notes |
|---|---|---|
| Tauri app shell | ~10 MB | Rust core + native webview |
| Bundled ffmpeg static binary | ~70 MB | Tauri sidecar; prebuilt per platform |
| Embedded Python runtime + deps | ~100 MB | `python-build-standalone` distribution |
| `whisper.cpp` binary | ~5 MB | Apple Metal on Mac, CPU/CUDA on Windows |
| Whisper "base" model | ~150 MB | Bundled good-enough default |

Target installer size: ~200 MB.

### First-launch downloads (optional, opt-in)

- Whisper large-v3 (~3 GB) for higher transcription accuracy

The first-launch wizard offers this as a one-click upgrade with a progress bar. The app remains usable on the bundled small model if the user skips the upgrade.

### Distribution phases

The architecture stays constant across phases — only the wrapping changes.

**Phase 0 — current MVP build.** No packaging. Run `make run-backend` and `make run-web` on a developer machine. Demo from the dev's laptop. The point is to validate the pipeline produces good clips before investing in installer plumbing.

**Phase 1 — early-user build.** Wrap the existing Next.js + FastAPI in a Tauri shell. Bundle ffmpeg, embedded Python, `whisper.cpp`, and the small ML models. Ship unsigned `.dmg` and `.exe` artifacts — early users can right-click → Open on Mac and click through SmartScreen on Windows. No auto-updater yet; ship via direct download.

**Phase 2 — distributable build.** Add Apple notarization and Windows code signing. Add an auto-updater (Tauri ships one). Mirror ML model downloads on a Chinese CDN (Alicloud OSS) since Hugging Face is throttled / blocked from mainland China — without this mirror the China build's first-launch download will fail.

### China-specific packaging notes

- **The model mirror on Alicloud OSS is mandatory for the China build.** Without it, first-launch model downloads fail in mainland China.
- **LLM provider selection happens at config time, not packaging time.** The same installer can target Claude (US dev) or Qwen / Kimi / DeepSeek (China prod) based on the active configuration profile.
- **No cloud storage in either region.** The workspace is a local directory the user picks at first launch and owns entirely.
